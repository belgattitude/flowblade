`@flowblade/source-duckdb` adapts [DuckDB](https://duckdb.org/) to Flowblade's
query, result, error, metadata, streaming and transaction APIs. It uses
[`@duckdb/node-api`](https://github.com/duckdb/duckdb-node-neo) and exports the
parameterized `sql` template tag.

## Install

```bash
npm install @flowblade/source-duckdb @duckdb/node-api
```

## Create a database and datasource

```typescript
import { DuckDBInstance } from "@duckdb/node-api";
import { DuckdbDatasource } from "@flowblade/source-duckdb";

const instance = await DuckDBInstance.create(":memory:", {
  access_mode: "READ_WRITE",
  max_memory: "64MB",
});
const connection = await instance.connect();
const ds = new DuckdbDatasource({ connection });
```

The instance and connection are application-owned resources. The datasource
does not close them. After stopping work that uses the datasource, close the
connection first and then the instance:

```typescript
connection.closeSync();
instance.closeSync();
```

## Parameterized queries

Use the exported `sql` tag to bind values. A type argument can describe the
result rows; it does not validate values returned by the database. Bind data
values rather than concatenating them into SQL text; dynamic SQL identifiers
must be handled separately and should only come from trusted input.

```typescript
import { DuckdbDatasource, sql } from "@flowblade/source-duckdb";

const query = sql<{ id: number; name: string }>`
  SELECT id, name
  FROM product
  WHERE category = ${category}
`;

const result = await ds.query(query, { name: "productsByCategory" });

if (result.error) {
  console.error(result.error.code, result.error.message, result.error.cause);
} else {
  console.log(result.data);
}

// Or throw on failure:
const { data: products, meta } = await ds.queryOrThrow(query);
```

`query()` and `queryOne()` return a `QResult` and do not throw.
`queryOrThrow()` and `queryOneOrThrow()` return data directly and throw
Flowblade's typed errors. DuckDB row values use its JSON-compatible row
conversion, so types such as timestamps are returned in JSON-compatible
forms. See [core contracts](/docs/core) for result narrowing, error codes, custom
error factories and metadata.

## Query one row

`queryOne()` returns a row or `null`, and reports `TOO_MANY_RESULTS` when
multiple rows match. `queryOneOrThrow()` expects exactly one row; use
`defaultValue` to supply a value when no row exists. Neither method rewrites
the SQL or adds a limit. If a query may return many rows, add a database-side
bound such as `LIMIT 2`.

## Streaming

`stream()` yields rows incrementally instead of collecting the full result in
application memory:

```typescript
const rows = ds.stream(
  sql<{ id: number }>`SELECT id FROM product ORDER BY id`,
  { name: "streamProducts" }
);

for await (const row of rows) {
  console.log(row.id);
  if (row.id >= 100) {
    break;
  }
}
```

Early exit is supported. DuckDB uses its own chunk size (2048 rows), so the
generic stream `chunkSize` option is ignored. Stream failures throw
`QErrors.QueryFailed` or `QErrors.Aborted` during iteration.

## Transactions and connection coordination

`transaction()` returns a result; `transactionOrThrow()` throws. The callback
receives a datasource (`tx`) bound to the transaction. Use and await `tx`
queries in the callback; nested transactions are not supported.

```typescript
const { data: count } = await ds.transactionOrThrow(
  async (tx) => {
    await tx.queryOrThrow(sql`DELETE FROM product WHERE expired`);
    await tx.queryOrThrow(sql`INSERT INTO product SELECT * FROM staging`);
    const { data: row } = await tx.queryOneOrThrow(
      sql<{ count: number }>`SELECT count(*)::INTEGER AS count FROM product`
    );
    return row.count;
  },
  { name: "refreshProducts", retry: { maxRetries: 3 } }
);
```

DuckDB uses snapshot isolation and does not support configurable isolation
levels or nested transactions. A failed query aborts the transaction; by
default (`onFailedQuery: "rollback"`), even a handled query error causes the
transaction to roll back. Prefer throwing query methods inside transaction
callbacks so failures cannot be accidentally ignored.

The adapter coordinates concurrent access to a shared connection. A
transaction holds the connection; other datasource queries and streams using
that connection wait until it ends, and active work completes before a
transaction begins. DuckDB conflicts can occur across connections to the same
database. Retries are opt-in, use exponential backoff with jitter, and rerun
the callback. Keep external side effects outside retried callbacks.

For direct driver access, `getConnection()` is an advanced, unstable API.
`withConnectionLock(connection, callback)` coordinates direct connection work
with datasource queries and transactions. Within a transaction callback, the
locked code runs on the transaction connection and failures prevent commit.
`isInConnectionTransaction(connection)` can be used to detect that context.

## Cancellation

Query methods, streams and transactions accept an `AbortSignal`. DuckDB
cancellation calls `connection.interrupt()`:

```typescript
const result = await ds.query(query, {
  signal: AbortSignal.timeout(5_000),
});
```

An aborted operation returns `ABORTED` from non-throwing methods or throws
`QErrors.Aborted` from throwing methods and streams. Its `cause` is the abort
reason. **Interruption applies to the connection:** it may stop whatever query
is currently running on that connection, so avoid sharing one connection
across unrelated work that must not be interrupted together.

## Logging

The adapter logs through LogTape in the `["flowblade", "duckdb"]` category.
Configure LogTape in your application to enable output. Logs include SQL and,
by default, bound parameters. Set `logParams: false` to omit parameters from
logs; they remain available in result metadata. A custom LogTape `logger` may
also be supplied.
